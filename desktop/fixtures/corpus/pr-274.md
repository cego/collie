After "Use glab's login" in Desktop, only the laptop appeared to keep the login, and vm-mk showed no GitLab login for gitlab.com.

No credentials were lost. The GitLab Connections check (`glabLoginOn`, from #260) chose its host from `GITLAB_HOST`, then `gitlab_host`, then glab's own default host. On vm-mk, glab's default host is gitlab.com. Everything else in Collie uses `gitlabHostOf`, which falls back to Collie's default, gitlab.cego.dk. That includes doctor, onboarding, and the Desktop code that gives the login. So Desktop gave vm-mk the gitlab.cego.dk login, and the check then asked about gitlab.com.

This PR makes two changes:

- **The check now uses Collie's host rule.** It calls `gitlabHostOf`, worked out on each Machine from its own settings, and no longer reads glab's default host.
- **"Use glab's login" now checks each target afterwards.** It reads the GitLab Connection on every Machine it gave the login to. A Machine that still shows no working login, or can't be checked, is reported as not given, with what it shows. Before, success was claimed as soon as glab accepted the token.

Secret handling is unchanged: the token still goes only to the chosen Machines' glab, on stdin, and the new check never reads tokens.

**Recovery for vm-mk:** nothing needs restoring. Once vm-mk and the laptop run a release with this fix, refresh Connections. For a correct reading on 0.108.2 before then, run `collie --machine vm-mk settings set gitlab_host gitlab.cego.dk`. That is a Flock-wide shared edit, so it was not run. Live access was never lost: the branch's check reads `ok · gitlab.cego.dk as mk` against vm-mk's real glab.
